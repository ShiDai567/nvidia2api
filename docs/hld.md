## 1. 文档目的

本文从系统层面说明 NVIDIA2API 的架构、模块、数据、接口、关键流程、安全和部署设计，为详细设计、实现和验收提供共同基线。需求优先级及验收条件以 [SRS](srs.md) 为准；本文不替代需求规格，也不代表设计中的能力已经实现或通过验证。

## 2. 设计范围与原则

### 2.1 范围

系统面向管理员自托管和受控调用方，首发覆盖 SRS 定义的单实例业务范围：NVIDIA Key、代理及分组、模型及能力矩阵、用户 API Key、OpenAI 风格调用、并发竞速、请求日志、独立用量、审计事件、Dashboard、运行配置和运维恢复。

### 2.2 约束

- 后端沿用 Django/DRF，前端沿用 Next.js App Router，数据持久化沿用 SQLite；不以重写或更换技术栈作为首发前提。
- 首发按一个后端 worker 进程设计。进程内 semaphore、共享 asyncio loop 和 HTTP 客户端池不提供跨进程协调保证。
- 多 worker、多实例、高可用、公众 SaaS、多租户隔离、PostgreSQL/Redis 迁移不在本设计支持范围内。
- 线路数量受可用 NVIDIA Key、启用代理、每请求线路上限和资源上限约束；启用代理数最多为可用 NVIDIA Key 数减一；同一请求内 NVIDIA Key 不重复。
- 竞速按首个有效 AI 响应选出 Winner。取消其他本地任务不保证上游未收到请求或未产生费用。
- OpenAI 兼容能力仅对完成验证的模型、客户端和参数组合声明。
- 容量、延迟、可用性和数据恢复目标须由运营方确定并通过目标环境验证，不在此虚构数值。

### 2.3 设计原则

1. API 层处理协议适配、认证入口、参数校验和响应组装；业务规则集中在服务层，持久化模型不承载跨模块调度逻辑。
2. 所有授权、模型白名单、配额、资源边界由后端强制执行，不能依赖控制台隐藏按钮或前端校验。
3. 凭据按用途分级保护：用户 API Key 仅存哈希，代理认证信息加密后存储，其他秘密通过部署配置注入并限制读取面。
4. 异步上游 I/O 与同步 Django 接口通过明确的生命周期边界衔接；流式资源许可覆盖完整 SSE 生命周期。
5. 关键状态变更、竞速结果、用量和诊断日志可关联追踪；未知用量不得伪装为真实用量。
6. 设计以可测试、可失败关闭和可恢复为目标；部署环境或外部依赖不可用时，不泄漏凭据或产生无界资源消耗。

## 3. 系统上下文与逻辑架构

### 3.1 系统上下文

```text
受控调用方 / OpenAI SDK                  管理员浏览器
          │ HTTPS + 用户 Bearer Key             │ HTTPS + 管理鉴权
          └──────────────────┬─────────────────┘
                             ▼
                   TLS 反向代理 / Web 入口
                   （SSE 关闭缓冲、长连接）
                             │
             ┌───────────────▼────────────────┐
             │       Django + DRF 单 worker    │
             │                                 │
             │ OpenAI API │ Admin API │ Health │
             │             API/Views            │
             ├─────────────────────────────────┤
             │ Key/代理/模型/用户Key 服务       │
             │ 路由构建、竞速、日志、用量、配置 │
             │             services/            │
             ├─────────────────────────────────┤
             │ SQLite │ 异步 HTTP 客户端/连接池 │
             └───────┬──────────────────┬──────┘
                     │                  │
               持久化数据         NVIDIA API / HTTP、HTTPS、
                                  SOCKS 代理线路
```

TLS 由受控入口终止。管理 API 需额外限制网络暴露；前端通过同源入口或明确配置的后端 API 地址访问管理接口。运行时必须维持单 worker，不能通过增加 worker 获得未经协调的并行能力。

### 3.2 分层与模块职责

| 层/模块 | 主要职责 | 设计边界 |
|---|---|---|
| Web 控制台（Next.js） | 管理员登录、资源 CRUD、批量操作、状态展示、对话调试、Dashboard、日志和用量查询 | 不存放上游秘密；所有业务约束由后端再次校验；展示真实服务端数据及明确空/错误状态 |
| OpenAI API（DRF） | `/v1/models`、`/v1/chat/completions`；认证、请求结构校验、错误格式、SSE 响应 | 不直接实现线路调度和数据库事务；返回行为受能力矩阵约束 |
| Admin API（DRF） | 管理认证、Key/代理/分组/模型/用户 Key/日志/用量/设置/Dashboard 操作 | 管理 token 通过受控配置；写入操作记录可审计事件；敏感字段默认脱敏 |
| 资源服务 | NVIDIA Key 调度/RPM、代理健康与启用约束、代理分组、模型同步/能力声明、用户 Key 验证与配额 | 原子计数和约束在后端实现；服务层可独立测试 |
| 请求编排服务 | 构造 Route、HTTP 客户端池、非流式/流式竞速、超时取消及结果汇总 | 每请求不复用 NVIDIA Key；Winner 判定一致；所有终态释放任务、响应、连接和并发许可 |
| 观测与运维服务 | Request ID、RequestLog、UsageRecord、审计事件、统计、保留清理和运行设置 | 诊断日志与计费/用量语义分离；不记录 prompt 或完整凭据 |
| SQLite | 业务配置、Key 元数据、模型、日志、用量和设置的持久化 | 单实例文件数据库；备份一致性、卷保护和恢复演练由部署流程保证 |
| 外部适配 | NVIDIA API、代理协议及外部模型/客户端 | 网络、限额、模型能力和可用性均为外部依赖，不由平台无条件保证 |

推荐后端边界对应当前目录：`backend/api/`、`backend/services/`、`backend/apps/core/`。当需求扩展时在现有边界内增量演进，不把 View 作为业务服务层。

## 4. 核心运行设计

### 4.1 聊天请求主流程

```text
客户端 POST /v1/chat/completions
  1. 生成 Request ID；校验请求体大小、JSON 结构及必需字段
  2. 校验用户 Bearer Key（哈希比对）、启用状态和模型权限
  3. 校验模型存在、启用状态及该模型能力矩阵中的参数规则
  4. 原子领取用户 RPM；取得全局/模型并发许可
  5. 选择可调度 NVIDIA Key 与健康代理，原子领取 Key RPM
  6. 构造不同 NVIDIA Key 的 Proxy + Key Route，并保留 Direct Route
  7. 并行调用各线路；逐线路记录成功、失败、超时或取消结果
  8. 以首个有效 AI 响应确定 Winner；取消其他线路
  9. 返回 JSON 或 SSE；汇总计数、RequestLog、UsageRecord 和审计/运行事件
 10. 在所有结束路径归还并发许可、关闭响应和回收任务/连接
```

前置认证、模型授权和参数错误在上游调用前拒绝。无可用 Route、上游全失败、请求超时、客户端断开和服务内部错误均需进入可诊断终态。请求 ID 应在响应头及相关日志中关联。

### 4.2 Route 构建与调度

调度候选由可用且未冷却的 NVIDIA Key 与可调度代理组成。代理按健康状态及已测延迟排序；Key 依据 RPM 额度、可用状态、冷却、最近使用和失败表现参与轮换。实际调度应遵守以下不变量：

```text
enabled_proxy_count <= max(available_nvidia_key_count - 1, 0)
route_count <= min(enabled_schedulable_proxy_count + 1,
                   available_key_count,
                   max_routes_per_request,
                   configured_resource_limit)
每个请求内，每个 NVIDIA Key 最多分配给一条 Route
Direct Route 使用一个独立 NVIDIA Key
```

Key RPM 通过数据库条件更新原子领取，不使用 SQLite `SELECT FOR UPDATE` 或读-改-写。代理启用/Key 删除等竞争管理操作必须在事务或等效串行化边界下维护代理数量不变量；请求构建时仍需重新校验，避免将界面状态当作最终约束。每次竞速实际启动 Route 数及各线路结局须可观测。

### 4.3 Winner 判定与失败处理

- **非流式**：HTTP 成功、响应可解析、存在有效 `choices`/`message` 或约定内容且不含上游 `error`，方可成为 Winner。HTTP 200 本身不代表成功。
- **流式**：SSE 至少产生一个可解析、含有效 AI `choices`/`delta` 且无错误的输出后方可成为 Winner。空流、错误 chunk、有效输出前 `[DONE]` 均不能胜出；Winner 后继续逐块转发至终止标记、异常或断开。
- 个别 Route 失败不提前终止其他候选；当全部线路失败时，返回有语义的 OpenAI 风格错误和适当 HTTP 状态。
- 401/403、429、上游 5xx、模型不存在、无效响应、网络错误、超时和取消分别归类；Key 与代理健康状态按错误归因独立更新。重试必须有界，不因请求级模型错误无意义重复调用。
- 取消为尽力而为：本地 task 取消并关闭响应，不宣称撤销上游已接收请求或费用。

### 4.4 流式资源生命周期

Winner 确认前，竞速等待首个有效 SSE 输出，以便全失败时仍可返回真实 JSON 错误状态。Winner 确认后，后台异步泵将上游行写入有界线程安全队列，由 Django `StreamingHttpResponse` 逐块 yield；泵不得阻塞等待整条流结束。全局/模型并发许可必须在 SSE 结束、异常、超时或客户端断开后才释放。`finally` 路径关闭 Winner 上游响应、取消并等待其他 task、结束日志/用量并释放许可。部署反向代理须关闭响应缓冲并设置适当长连接超时。

### 4.5 HTTP 客户端与资源控制

异步 HTTP 客户端按线路/代理配置复用连接池，支持 HTTP、HTTPS、SOCKS5/SOCKS5H。客户端有明确创建、复用、失效和关闭生命周期；代理凭据只在构造所需连接配置时解密，禁止进入日志。请求体大小、每请求 Route 数、全局/用户/模型并发、上游连接数、连接/读取/总超时、流式时长及重试均有有效配置边界。竞速 task、队列和连接不可无界创建。参数具体值由 TBD 输入及压测确定。

## 5. 数据设计

### 5.1 逻辑实体

```text
ProxyGroup 1 ─── n Proxy
UserApiKey 1 ─── n RequestLog
RequestLog 1 ─── 0..1 UsageRecord（按成功/可用用量创建）
RequestLog 1 ─── n RouteOutcome（可规范化实体，或兼容期存 JSON）
NvidiaApiKey / AIModel / SystemSetting / AuditEvent 为独立或弱关联实体
```

| 实体 | 主要职责与关键数据 | 约束/说明 |
|---|---|---|
| `NvidiaApiKey` | 加密或受保护的上游凭据、状态、RPM 窗口、成功/失败计数、冷却、最近使用 | 唯一凭据标识；列表默认脱敏；RPM 领取需原子化 |
| `ProxyGroup` | 分组名称、描述、时间戳 | 名称唯一性按产品规则确定；删除关联代理的行为需定义并测试 |
| `Proxy` | 协议、主机端口、加密认证信息、分组、地理/IP 元数据、启用/健康/延迟/冷却/计数 | 端点唯一约束；认证信息密文；支持批量导入和健康检测 |
| `AIModel` | 模型名称、提供方、元数据、状态、启用标志 | 上游同步幂等；软下架/手动模型处理规则明确 |
| `ModelCapability` | 模型与能力/参数、验证状态、行为规则、证据/更新时间 | 能力可接受、拒绝或忽略；未验证不得标成支持 |
| `UserApiKey` | 名称、SHA-256 哈希、展示前缀、启用、RPM、允许模型、请求计数 | 明文只在创建时返回一次；哈希唯一；并发额度和计数原子正确 |
| `RequestLog` | Request ID、用户 Key、模型、时间/状态/耗时、流式/TTFT、HTTP 错误、Winner、线路摘要 | 不保存 prompt/完整凭据；索引支持时间、状态、模型和用户 Key 查询 |
| `RouteOutcome` | Route 类型、Key/代理标识、状态、延迟、错误类别、HTTP 状态及取消原因 | 每条实际启动线路有结果；可保留 JSON 结构或后续规范化 |
| `UsageRecord` | RequestLog 关联、用户 Key、模型、输入/输出/总/缓存 token、来源与可信状态 | 与诊断日志分离；未知/估算值显式标记，不伪造为真实值 |
| `AuditEvent` | 主体、动作、目标、时间、结果及安全上下文 | 覆盖 Key/代理/模型/设置等敏感状态变更；不含秘密值 |
| `SystemSetting` | 可运行时修改的非秘密业务参数及描述 | 通过注册表限制类型/范围；秘密和加密密钥不放入数据库运行设置 |

以上是目标逻辑模型。当前仓库已有 `NvidiaApiKey`、`Proxy`、`AIModel`、`UserApiKey`、`RequestLog`、`SystemSetting`；`ProxyGroup`、`ModelCapability`、独立 `UsageRecord`、`AuditEvent` 为 SRS 首发目标中的设计增量，不能据本文误认为已存在。实际字段、迁移和删除策略在详细设计与迁移方案中确定。

### 5.2 一致性、索引与保留

- Key RPM 和用户 Key RPM 均使用条件更新或经验证的等价原子方案；成功/失败计数采用数据库原子增量，避免并发丢失。
- 代理启用上限并发变更须串行化检查和写入；事务失败时不返回成功状态。
- 为 Request ID、用户 Key、模型、创建时间、状态及管理筛选组合建立适当索引；索引需经查询使用模式验证，控制 SQLite 写入成本。
- RequestLog 与 UsageRecord 分别支持诊断查询和用量汇总。清理任务遵守经批准的保留期，并保证关联记录策略明确。
- SQLite 备份需使用一致性备份方案或受控停写/快照流程；备份保存在数据库文件之外的受保护位置并执行独立恢复演练。

## 6. 接口设计

### 6.1 用户 OpenAI 风格 API

| 方法与路径 | 认证 | 设计行为 |
|---|---|---|
| `GET /v1/models` | `Authorization: Bearer <user-api-key>` | 返回已启用且获当前 Key 授权的模型；按能力/兼容策略决定附加元数据 |
| `POST /v1/chat/completions` | `Authorization: Bearer <user-api-key>` | 校验模型及能力矩阵，按 Route 竞速；支持已验证的非流式和 SSE 行为 |
| `GET /health` | 无 | 健康探针，不暴露敏感配置或内部状态细节 |

参数支持按 `AIModel` 的能力声明执行；对不支持参数采取明确的拒绝、忽略或透传策略，并对外文档化。错误统一采用 OpenAI 风格 `error.message/type/param/code` 对象和与语义相符的 HTTP 状态。SSE 在确认 Winner 后返回 `text/event-stream`，逐块 flush 并正确结束；代理层不得缓冲。

### 6.2 管理 API 与控制台

管理接口使用 `/api/admin/` 命名空间，固定管理 token 通过受控环境配置注入，按 SRS 以 Bearer 管理鉴权为规范；现有客户端/端点兼容行为应在实现迁移时统一并验证。管理面通过 TLS 暴露且由网络策略限制访问。接口域包括：

- Dashboard 与用量趋势/汇总；
- NVIDIA Key CRUD、导入、批量操作及连通测试；
- 代理 CRUD、导入、检测、测速、IP 查询、批量操作和代理分组；
- 模型同步、启停、元数据及能力矩阵；
- 用户 API Key 创建/禁用/撤销、RPM、模型白名单和统计；
- 请求日志、线路详情、用量记录、审计事件查询；
- 非秘密运行设置、日志/用量保留操作。

列表接口采用一致的分页、过滤和排序约定；敏感字段默认脱敏。用户 API Key 创建响应是唯一展示完整 Key 的接口时点。所有写操作重新校验引用对象和业务不变量，并按需写审计事件。

### 6.3 上游适配

NVIDIA 上游通过可配置 base URL 和 httpx 异步请求访问。请求只转发能力矩阵允许的参数，统一处理上游状态、错误体、超时和响应解析。上游模型同步和聊天调用分别处理；上游变化不能未经兼容测试直接变成平台保证。

## 7. 安全与隐私设计

| 资产/边界 | 设计控制 |
|---|---|
| 用户 API Key | 高熵随机生成；数据库仅存 SHA-256 哈希与必要前缀；比较时不泄漏时序信息；支持禁用/撤销；创建时仅展示一次 |
| NVIDIA Key | 持久化和管理 API 采用受限访问；列表脱敏；日志、错误和导出不出现完整凭据；轮换/撤销按运维流程执行 |
| 代理凭据 | 使用数据库外注入的密钥进行加密后持久化；读取权限最小化；提供密钥版本/轮换迁移和失败关闭行为；备份同样受保护 |
| 管理 token、Django 签名密钥 | 由安全配置注入，不存 SQLite；生产启动拒绝缺失、弱化或已知开发默认值；固定 token 鉴权并常数时间比较 |
| API 与管理网络 | TLS；管理 API 网络白名单/内网或额外入口控制；反向代理正确处理可信头和来源；限制请求体与超时 |
| 日志与错误追踪 | 禁止记录 Authorization、Key 全文、代理密码及默认情况下的 prompt/完整请求体；异常摘要脱敏；Request ID 可关联但不可作为凭据 |
| 管理写操作 | 服务端鉴权和授权、输入校验、ORM 参数化访问；记录主体/动作/目标/结果，不记录秘密值；防 CSRF/XSS/越权 |
| 生产配置 | 必需密钥缺失或默认值时失败关闭；生产 DEBUG 关闭；数据库卷、备份和配置权限纳入部署检查 |

加密算法、密钥封装和轮换步骤由详细安全设计确定，并须验证密文迁移、恢复和旧密钥失效；SRS-F-029 未验收前不得以“字段非明文”替代密钥生命周期设计。

## 8. 可靠性、可观测性与运维

- 每个请求生成唯一 Request ID，贯穿用户响应、RequestLog 和各 RouteOutcome；请求和线路的最终状态可区分成功、失败、超时、取消及客户端断开。
- 核心指标包括请求数/成功率/延迟/TTFT、活跃并发、Route 启动与成功失败取消数、Key/代理健康分布、用量及数据库/资源错误。Dashboard 仅显示真实数据和明确空状态。
- 日志记录结构化错误类别和操作上下文，避免凭据及默认 prompt 内容；敏感管理操作写 AuditEvent。
- 所有 HTTP 调用有连接、读取和总超时；重试、竞速数、队列和并发有硬上限。流式连接断开要能终止本地读取并完成清理。
- 日志/用量保留策略、归档/清理任务、SQLite 备份频率和 RPO/RTO 由运营方批准；实施前完成独立恢复演练。
- 运行时设置覆盖范围、类型和上下限通过注册表维护；仅允许热更新明确安全的配置，连接池、密钥和部署拓扑类配置按需重启生效。
- 发布门禁按 SRS-F-040 执行：后端测试、前后端 lint/build、Docker 启动冒烟、目标 NVIDIA/代理真实冒烟；压测和恢复演练结果单独留档。

## 9. 部署架构

```text
Internet / 内部调用网络
          │ TLS
          ▼
受控 Nginx / Caddy
  ├─ /api、/v1 → 单一 Django 后端 worker
  │                ├─ SQLite 持久卷（data/）
  │                └─ NVIDIA API / HTTP(S)、SOCKS 代理
  └─ /          → Next.js standalone 控制台

部署配置：环境注入的 SECRET_KEY、ADMIN_TOKEN、凭据加密密钥等
```

Docker Compose/单镜像部署应持久化 SQLite 数据目录，配置健康检查、受控网络、TLS 入口、日志采集和备份任务。后端必须以单 worker 运行，验证连接池与 semaphore 行为。Next.js 到后端的 `/api`、`/v1` 反向代理按实际部署配置；SSE 路径关闭缓冲并配置覆盖业务超时的读取期限。生产默认凭据和缺失的秘密必须令启动失败。

从开发到生产的配置差异、环境变量、初始化管理员、迁移、回滚、备份恢复和 SSE 配置以 [deployment.md](deployment.md) 为运维手册补充；目标部署拓扑需在发布前验证，而不只依赖设计图。
